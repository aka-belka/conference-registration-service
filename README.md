# Сервис регистрации участников конференции

Учебное веб-приложение на Django для управления участниками конференции, мероприятиями и билетами.

## 1. Назначение проекта

Сервис регистрации участников конференции — учебное приложение, которое позволяет хранить сведения об участниках, мероприятиях и билетах, выполнять основные операции с этими объектами и предоставлять доступ к информации через веб-интерфейс на Django.

Проект развивается поэтапно:

- **ПР1–ПР3** — разработка консольной версии приложения и предметных классов;
- **ПР5** — создание веб-интерфейса;
- **ПР6** — переход на систему шаблонов Django;
- **ПР7** — организация реляционного хранения данных в SQLite;
- **ПР9** — переход на Django ORM;
- **ПР10** — расширение административной панели, работа с данными через ORM, фильтрация, сортировка, пагинация, агрегирование и анализ SQL-запросов.

## 3. Предметная область

В системе используются три основные сущности:

- **Участник (Participant)** — идентификатор, имя и адрес электронной почты;
- **Мероприятие (Event)** — идентификатор, название, дата проведения и максимальное количество мест;
- **Билет (Ticket)** — идентификатор, связь с мероприятием и участником, статус и номер билета.

Для предметной области реализованы собственные Python-классы `Participant`, `Event` и `Ticket` (пакет `models/`), а также Django-модели в приложениях `participants` и `events`.

### 3.1. Django-модели (ПР9)

- `Participant` (`participants/models.py`): `name`, `email`.
- `Event` (`events/models.py`): `title`, `date`, `max_seats`.
- `Ticket` (`events/models.py`): `event` (FK → `Event`), `participant` (FK → `Participant`), `status`, `number`.

Связи между моделями:

- `Ticket.event` → `Event`;
- `Ticket.participant` → `Participant`.

Для связей используется `ForeignKey` с `on_delete=CASCADE` и `related_name='tickets'`.

Количество зарегистрированных участников и свободных мест для мероприятия рассчитывается с помощью ORM-аннотаций, а не хранится в отдельном поле модели `Event`.

### 3.2. Статусы билетов (ПР10)

Для статусов билетов используется `TextChoices`:

- `BOOKED` — забронирован;
- `PAID` — оплачен;
- `CANCELLED` — отменён.

Статусы применяются при фильтрации билетов, подсчёте статистики и определении количества занятых мест.

Отменённые билеты не учитываются при расчёте занятых мест.

### 3.3. Исходная база данных (ПР7)

На этапе ПР7 данные были перенесены из JSON-файлов в базу данных SQLite (`data/conference.sqlite`).

Эта база сохранена как источник исходных данных и предыдущая реализация хранения. После перехода на Django ORM веб-представления используют основную базу данных Django — `db.sqlite3`.

## 5. Веб-интерфейс

Веб-часть приложения реализована на Django.

Основные страницы:

- `/` — главная страница;
- `/participants/` — список участников;
- `/participants/<id>/` — информация об участнике;
- `/events/` — список мероприятий;
- `/events/<id>/` — информация о мероприятии;
- `/events/search_events/` — поиск мероприятий по названию и дате;
- `/events/statistics/` — статистика по билетам и мероприятиям;
- `/tickets/` — список билетов с фильтрацией, сортировкой и пагинацией;
- `/admin/` — административная панель Django.
- `/tickets/create/` — создание билета;
- `/tickets/<id>/edit/` — редактирование билета;
- `/tickets/<id>/cancel/` — отмена билета через POST-запрос.

Для формирования страниц используются Django-шаблоны. Генерация HTML непосредственно в Python-коде веб-представлений не применяется: view-функции подготавливают контекст и вызывают `render()`.

### 5.1. Поиск мероприятий

На странице поиска предусмотрен поиск мероприятий по названию и дате проведения.

Для обработки параметров используются GET-запросы. Результаты поиска отображаются с пагинацией.

### 5.2. Работа со списком билетов

На странице `/tickets/` реализованы:

- фильтрация билетов по мероприятию;
- фильтрация по статусу;
- сортировка по номеру билета;
- сортировка по дате мероприятия;
- сортировка по имени участника;
- постраничное отображение результатов.

Параметры фильтрации и сортировки сохраняются при переходе между страницами пагинации.

### 5.3. Свободные места

Для мероприятий рассчитываются количество зарегистрированных участников и количество свободных мест.

При подсчёте занятых мест учитываются билеты со статусами «забронирован» и «оплачен». Отменённые билеты не уменьшают количество свободных мест.

## 6. Django Template Language

Шаблоны используют возможности Django Template Language.

### 6.1. Базовый шаблон

Общий шаблон страниц: `templates/base.html`.

Он содержит HTML-структуру страницы, подключение Bootstrap и собственного CSS, логотип, навигацию, футер и блоки:

```django
{% block title %}{% endblock %}
{% block content %}{% endblock %}
```

Дочерние шаблоны наследуют базовый шаблон:

```django
{% extends "base.html" %}
```

### 6.2. Включаемые шаблоны

Повторяющиеся фрагменты вынесены в отдельные шаблоны:

- `includes/navigation.html` — навигационное меню;
- `participants/includes/participant_card.html` — карточка участника;
- `events/includes/event_card.html` — карточка мероприятия.

Подключение выполняется через:

```django
{% include "includes/navigation.html" %}
{% include "participants/includes/participant_card.html" %}
{% include "events/includes/event_card.html" %}
```

### 6.3. Контекст

View-функции передают данные в шаблоны через словарь контекста:

```python
context = {
    "participants": participants_list,
}
return render(request, "participants/participant_list.html", context)
```

В шаблоне данные доступны по имени переменной:

```django
{% for participant in participants %}
    ...
{% endfor %}
```

Аналогичным образом передаются `events` и `tickets`.

### 6.4. Циклы и условия

Для перебора коллекций используется конструкция:

```django
{% for participant in participants %}
    ...
{% empty %}
    <li class="list-group-item">Участники не найдены.</li>
{% endfor %}
```

Для условного отображения применяется конструкция `{% if %}`. Например, на странице участника можно проверить наличие объекта:

```django
{% if participant %}
    ...
{% else %}
    <h1 class="text-danger">Участник не найден</h1>
{% endif %}
```

### 6.5. Фильтры шаблонов

В шаблонах используются стандартные фильтры Django:

- количество элементов: `{{ events|length }}`;
- значение по умолчанию: `{{ event.title|default:"Без названия" }}`.

Фильтры используются для представления данных и не содержат бизнес-логику приложения.

### 6.6. URL-маршрутизация

Для страниц используются именованные маршруты с пространствами имён:

```django
{% url 'homepage:index' %}
{% url 'participants:participants' %}
{% url 'participants:participant_detail' participant.id %}
{% url 'events:events' %}
{% url 'events:event_detail' event.id %}
{% url 'events:search_events' %}
{% url 'events:statistics' %}
{% url 'tickets' %}
```

Для приложений заданы `app_name` (`homepage`, `participants`, `events`), что позволяет обращаться к маршрутам через `app:name`.

Ссылки в шаблонах формируются с помощью `{% url %}`. Для списка билетов используется именованный маршрут `tickets`, который ведёт на представление с фильтрацией, сортировкой и пагинацией.

## 8. Хранение данных

Основная база данных веб-приложения — SQLite (`db.sqlite3`), работа с которой выполняется через Django ORM.

- Модели: `Participant` (`participants/models.py`), `Event` и `Ticket` (`events/models.py`).
- Связи: `Ticket.event` → `Event`, `Ticket.participant` → `Participant`.
- Миграции моделей находятся в `participants/migrations/` и `events/migrations/`.
- Представления получают и обрабатывают данные через Django ORM.
- Исходные JSON-файлы и база ПР7 сохранены в проекте как предыдущие источники данных.
- SQL-слой ПР7 (`sql/schema.sql`, `sql/queries.sql`, `db/database.py`) сохранён как предыдущая реализация хранения данных.

### 8.1. ORM-запросы проекта (ПР9–ПР10)

В представлениях используются следующие возможности Django ORM:

- получение записей: `all()`, `get_object_or_404()`;
- фильтрация: `filter()`;
- исключение записей: `exclude()`;
- сложные условия: `Q`;
- сортировка: `order_by()`;
- работа со связанными объектами: `select_related()`;
- аннотирование: `annotate()`;
- агрегирование: `aggregate()`;
- подсчёт записей: `Count`;
- вычисления с полями модели: `F`;
- статистические функции: `Avg`, `Min`, `Max`;
- постраничное отображение: `Paginator`.

Для поиска мероприятий используются фильтрация по названию и дате. Для билетов применяются фильтры по мероприятию и статусу, а также сортировка по выбранному полю.

### 8.2. Менеджер и QuerySet билетов (ПР10)

Для модели `Ticket` реализованы собственные методы QuerySet и менеджера, позволяющие получать билеты по заданным условиям.

Используются методы для получения:

- забронированных билетов;
- оплаченных билетов;
- отменённых билетов;
- активных билетов;
- билетов по дате;
- билетов определённого мероприятия.

Это позволяет повторно использовать условия запросов и не дублировать одинаковую логику в представлениях.

### 8.3. Аннотирование и агрегирование (ПР10)

Для получения дополнительных показателей используются `annotate()` и `aggregate()`.

В частности:

- для мероприятий рассчитывается количество зарегистрированных билетов;
- вычисляется количество свободных мест;
- формируется статистика по статусам билетов;
- рассчитываются общие и дополнительные показатели по мероприятиям и билетам.

При подсчёте зарегистрированных билетов отменённые билеты исключаются из расчёта занятых мест.

### 8.4. Оптимизация запросов (ПР10)

Для уменьшения количества дополнительных обращений к базе данных используется `select_related()` при получении билетов вместе со связанными мероприятиями и участниками.

Для страниц со списками применяется пагинация через `Paginator`. При этом Django выполняет отдельный запрос для подсчёта общего количества записей и запрос для получения записей текущей страницы.

Для анализа SQL-запросов используется Django Debug Toolbar.

### 8.5. Формы Django (ПР11)

Для работы с билетами реализованы две формы в `events/forms.py`.

**TicketFilterForm (forms.Form)** используется для фильтрации списка билетов.

Поддерживаемые параметры:
- мероприятие;
- статус билета;
- дата мероприятия;
- сортировка по номеру, дате мероприятия и имени участника.

Данные формы передаются через GET-параметры. Проверка выполняется методом `is_valid()`, проверенные значения извлекаются через `cleaned_data`.

**TicketForm (forms.ModelForm)** используется для создания и редактирования билетов на основе модели `Ticket`.

Настроены:
- подписи полей (`labels`);
- HTML-виджеты (`widgets`);
- CSS-классы Bootstrap;
- подсказка для номера билета;
- пользовательская проверка в методе `clean()`.

При создании и редактировании проверяются:
- наличие другого активного билета этого участника на выбранное мероприятие;
- наличие свободных мест;
- уникальность номера билета.

При создании билета участник выбирается из списка. При редактировании имя владельца отображается отдельно, а изменение участника через форму не предусмотрено.

**Создание и редактирование билетов**

Представления `ticket_create()` и `ticket_update()` обрабатывают GET- и POST-запросы.

При успешной проверке данные сохраняются через `form.save()`. При ошибках форма отображается повторно с сообщениями валидации.

**Отмена билетов**

Представление `ticket_cancel()` принимает только POST-запросы. При отмене статус билета меняется на `отменён`, запись остаётся в базе данных.

Отменённые билеты не учитываются при проверке занятости мест и не блокируют повторную регистрацию участника.

Для получения несуществующего билета используется `get_object_or_404()`.

POST-формы защищены CSRF-токеном.

Загрузка изображений не реализована, поскольку модели проекта не предусматривают соответствующих полей.

## 9. Административная панель Django (ПР10)

Для управления данными используется встроенная административная панель Django, доступная по адресу `/admin/`.

В административной панели зарегистрированы модели участников, мероприятий и билетов.

Для удобства работы с данными настроены:

- отображение выбранных полей в списках записей;
- поиск по основным полям;
- сортировка записей;
- ограничение количества записей на странице;
- отображение связанных билетов непосредственно в карточках мероприятий и участников.

Для мероприятий и участников используются встроенные формы редактирования связанных билетов (Inline).

Административная панель позволяет просматривать, добавлять, изменять и удалять записи без необходимости выполнять эти операции через пользовательские страницы приложения.
